# Events, time and the plugin context

## Listening

```dart
final sub = context.listen(Events.playerJoin, (server, event) {
  logger.info('${event.player.getName()} joined');
});
sub.cancel();                       // stop listening
```

`listen` observes, `intercept` changes or cancels the event (the server waits for
it). Events with a `cancelled` field have a generated `cancel()`:

```dart
context.intercept(Events.playerChat, (server, event) => event.cancel());
```

The server can't unregister a handler, so `cancel()` makes it inert: it stays
registered but is ignored.

`context.once(kind, handler, where: ...)` runs for the first matching event only.

### Many handlers for one event

Every `listen`/`intercept` call registers a handler of its own with the host, and
the host crosses into the plugin once per registered handler for **every** event
of that kind. A plugin with a handler per block, item or position therefore pays
one round trip per registered handler and per event, which is far more than the
handler's own work.

`listenGroup` and `interceptGroup` register **one** handler with the host and run
the plugin's handlers itself, in the order they were added:

```dart
final placed = context.listenGroup(Events.customBlockPlaced);
for (final block in blocks) {
  placed.add(handlerOf(block), where: (e) => e.block == block);
}
```

A member sees a `where`-accepted event exactly as a `listen` of its own would
have: it runs in its own callback scope, one member's failure does not stop the
others, and a member that waits for a timer does not hold the server. Cancelling
a member's subscription takes that member out and leaves the group's other
members listening. `registerBlockBehavior` uses a group for every hook, so a
block behavior costs one host handler per hook and not one per block.

## Waiting for an event

```dart
sender.reply('Type your answer in chat.');
final chat = await context.next(
  Events.playerChat,
  where: (chat) => chat.player.getName() == name,
  timeout: const Duration(seconds: 30),
);   // throws TimeoutException if nobody answers
```

The event's resources (like its `player`) are valid until your code first awaits
again, so read what you need right away.

## Events added for plugin blocks, entities, menus and data

All have a typed entry in `Events` (generated by `tool/generate_events.dart`, so
the list follows the WIT) and work with `listen`, `intercept`, `once` and `next`.
Events with a `cancelled` field have `cancel()`.

| Group | Events |
| --- | --- |
| Block callbacks | `customBlockNeighborUpdate`, `customBlockPlaced`, `customBlockStateReplaced`, `customBlockBroken`, `customBlockScheduledTick`, `customBlockRandomTick`, `customBlockEntityCollision`, `customBlockEntityStep`, `customBlockCanPlace`, `customBlockUpdateShape`, `customBlockRedstonePower`, `customBlockComparatorOutput` (use `registerBlockBehavior`, [block-callbacks.md](block-callbacks.md)) |
| Block callbacks (more) | `customBlockShape`, `customBlockUse`, `customBlockAttack`, `customBlockCloneItem`, `customBlockPlayerWillDestroy`, `customBlockPhysics`, `customBlockLanded`, `customBlockCondition`, `customBlockSoundType`, `customBlockFireSpread` |
| Plugin entities | `pluginVehicleInput`, `entityStartTracking`, `entityStopTracking`, `entityItemUpdate` (after `Context.tickItemEntities`) |
| Mixin style hooks | `entityFluidMovement` (flag `fluidMovementEvents`), `fluidCanPassThrough`, `itemUseTick`, `itemSwing`, `itemUseFirst` (`useResult`), `canAttackBlock`, `fakePlayerPlaceCheck` |
| Data | `datapackReload`, `tagsUpdated`, `datapackSync` (`reload`), `lootModify` (change `loot`, or `cancel()`) |
| Worldgen | `pluginFeaturePlace` ([worldgen-features.md](worldgen-features.md)) |
| Ticking | `worldTick`, `blockEntityTick` (batched positions per type), `playerTick`, `entityTick` (after `context.tickEntities`), `entityEnteringSection` |
| Living entities | `livingDrops`, `livingEquipmentChange`, `livingBreathe`, `livingVisibility`, `entitySize` |
| Items | `playerUseItem`, `playerUseBlock` (with hit position and face) |
| Menus | `menuClick`, `menuSlotChanged`, `menuButtonClick`, `menuClosed` |
| Block entities | `blockEntityLoad`, `blockEntityUnload` |
| Connection phases | `loginStart`, `loginQueryAnswer`, `configurationPreBrand`, `configurationStart`, `configurationPayload`, `configurationEnd`, `configurationPacketReceived`, `configurationFinish` |

```dart
context.listen(Events.worldTick, (server, e) { /* e.tick */ });
context.intercept(Events.livingDrops, (server, e) =>
    e.copyWith(drops: [...e.drops]));            // change the drops
context.listen(Events.blockEntityTick, (server, e) {
  for (final pos in e.positions) { /* one call per chunk batch */ }
});
```

The per-tick events run on every tick: keep the handlers short.

## `Plugin.context`

The `context` parameter of `onLoad` is only valid while it runs. `Plugin.context`
is the same context, kept for as long as the plugin is loaded, so command handlers
and other later callbacks can register events and use `next`.

## Time

The server runs 20 ticks per second. Prefer durations:

```dart
server.after(const Duration(seconds: 5), (server) => ...);
final task = server.every(const Duration(minutes: 1), (server) => ...);
task.cancel();
```

Durations round up to whole ticks (50ms). `20.ticks` is a one second `Duration`.
`Debouncer` and `Throttle` smooth out bursts of calls.

## Enum names

Every enum has `wireName` (its name in the WIT, like `iron-golem`) and
`fromWireName`:

```dart
EntityType.ironGolem.wireName;          // 'iron-golem'
EntityType.fromWireName('iron-golem');  // EntityType.ironGolem
```
