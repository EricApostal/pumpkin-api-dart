# Placement rule host gaps

Several Create blocks cannot state their Java `getStateForPlacement` exactly with the current
`block-placement` rule vocabulary. Their rule lists use the nearest expressible stand-in, and
`test/placement_parity_test.dart` skips exactly the placements that need the missing source
(`_Target.skip`) while pinning the fallback in `placement rules the host cannot express`.

This is the proposal for the host additions that would let those branches be stated exactly.
Nothing here is implemented; the host lives in the Pumpkin repo
(`crates/pumpkin-plugin-wit/v0.2/block-placement.wit`,
`crates/pumpkin-data/src/block_registry.rs`,
`crates/pumpkin-core/src/block/blocks/dynamic.rs`).

## Summary

| # | Addition | Kind | Unblocks |
|---|---|---|---|
| 1 | `looking-axis` | `placement-source` variant, no payload | linear/secondary/radial chassis (look-axis branch) |
| 2 | `clicked-block-property(clicked-block)` | variant + record | linear/secondary chassis (chassis-on-chassis), attached actors (actor-on-actor) |
| 3 | `clicked-horizontal-face` | variant, no payload | belt funnels (side click), attached actors (side click), item hatch (side click) |
| 4 | `refuse-when-clicked-face-axis` | `placement-rule` field, `option<block-axis>` | item hatch (no placement on a top or bottom click) |
| 5 | `neighbour-shaft-axis`, `when-neighbour-shaft` | variant + `placement-rule` field | chassis shaft branches (needed for exactness, see below) |
| 6 | `when-clicked-face-axis` | `placement-rule` field, `option<axis-filter>` | attached actors (`else if` only for a horizontal click) |

Items 5 and 6 were not in the request. Item 5 is needed for the chassis branches to be exact at
all, and item 2 is not exact without item 6 (Java copies the clicked actor's facing only for a
horizontal click), so both are specified here too.

## Common touch points

Every addition touches the same five places, in this order:

1. `crates/pumpkin-plugin-wit/v0.2/block-placement.wit` — the variant, record and field shapes
   above. The Dart bindings are generated from this file (`bindings.g.dart`), so nothing else in
   `packages/pumpkin_api` is generated by hand.
2. `crates/pumpkin-data/src/block_registry.rs` — `PlacementSource` (variant, `required_values`,
   `value`), `PlacementRule` (new fields), `PlacementContext` (new fields), the validation in
   `resolve_placement_rules`, and `state_for_placement` (skip rules whose conditions fail).
3. `crates/pumpkin-core/src/block/blocks/dynamic.rs` — fill the new `PlacementContext` fields in
   `DynamicBlock::on_place`; the veto in `can_place_at`.
4. `crates/pumpkin-wasm-host-v0_2/src/block_placement.rs` — `from_wit_source` and
   `from_wit_rule` (`:20-49`) copy the new variants and fields across.
5. `packages/pumpkin_api/lib/src/block_placement_core.dart` and `block_placement.dart` — the
   `PlacementSourceKind` value, the `PlacementRule` constructor, and `_toWire`.

## 1. `looking-axis`

### Java call site

`content/contraptions/chassis/LinearChassisBlock.java:44-58` (the non-sneaking branch) and
`content/kinetics/base/RotatedPillarKineticBlock.java:68-80` (the `super` call of both chassis
classes, and the whole rule of `RadialChassisBlock`):

```java
return defaultBlockState().setValue(AXIS, context.getNearestLookingDirection().getAxis());
```

`getNearestLookingDirection()` is the dominant of all six look directions, so its axis is `y` for
a steep look down or up. `horizontal-axis` cannot express that: it is the axis of
`getHorizontalDirection()`, which has no `y`.

### WIT

```wit
    variant placement-source {
        // ...
        /// The axis of the direction the player looks at: `x`, `y` or `z`. `opposite` is not
        /// allowed. Unlike `horizontal-axis` this is `y` when the look is mostly vertical.
        looking-axis,
    }
```

### Host

* `PlacementSource::LookingAxis`, `required_values` → `["x", "y", "z"]`,
  `value` → axis name of `context.looking_direction`; reject `opposite` in the same arm that
  rejects it for `clicked-axis` and `horizontal-axis`
  (`block_registry.rs`, the `ClickedAxis | HorizontalAxis | TrackShape | Constant` match arm).
* No change to `PlacementContext`: `looking_direction` is already there.

### Dart

`PlacementSourceKind.lookingAxis` + `PlacementRule.lookingAxis(String property, {bool? whenSneaking})`
in `packages/pumpkin_api/lib/src/block_placement_core.dart`, one arm in
`HostBlockPlacement._toWire`, and the generated binding after the WIT is rebuilt.

### Unblocks

The chassis look-axis branch of both linear chassis and of the radial chassis (together with 5).

## 2. `clicked-block-property`

### Java call sites

`content/contraptions/chassis/LinearChassisBlock.java:48-56`:

```java
BlockState blockState = context.getLevel().getBlockState(placedOnPos);
if (isChassis(blockState))
    return defaultBlockState().setValue(AXIS, blockState.getValue(AXIS));
```

`LinearChassisBlock.isChassis` (`:83`) accepts `LINEAR_CHASSIS` **or** `SECONDARY_LINEAR_CHASSIS`,
so the check is a set of blocks, not "the same block".

`content/contraptions/actors/AttachedActorBlock.java:70-75`:

```java
BlockState blockState = context.getLevel().getBlockState(context.getClickedPos()
    .relative(context.getClickedFace().getOpposite()));
if (blockState.getBlock() instanceof AttachedActorBlock)
    facing = blockState.getValue(FACING);
```

`instanceof AttachedActorBlock` covers the harvester, the plough and the roller.

### WIT

```wit
    /// A clicked block whose own property a rule reads. Only blocks a plugin registered are
    /// read; a vanilla block never gives a value.
    record clicked-block {
        /// Block keys that count (`create:linear_chassis`). A block of any other key gives no
        /// value, so the rule falls through to the next one.
        blocks: list<string>,
        /// The property to read (`axis`, `facing`). Its values must be ones the rule's property
        /// lists too.
        property: string,
    }

    variant placement-source {
        // ...
        /// The value of the clicked block's `property`, when the clicked block is one of
        /// `blocks`. `opposite` flips the value like the direction sources do.
        clicked-block-property(clicked-block),
    }
```

### Host

* `PlacementContext` gains the clicked block, computed in `DynamicBlock::on_place` from the
  already available world:

  ```rust
  clicked: args.world.get_block_and_state_id(
      &args.position.offset(args.direction.opposite().to_offset())),
  ```

  as `PlacementNeighbour`. This is the same pair the rule needs; no new world query kind.
* `required_values` → the clicked block's property values are not known at rule-set time (the
  clicked block can be any of `blocks`), so validation must check that the rule's *own* property
  lists the value names of the declared `property` for each listed block. Simplest correct form:
  require the rule's property values to be a superset of every listed block's `property` values,
  and fail otherwise (the existing "property has no value X" error).
* `value` → `Some(context.clicked.property(rule.property))` when the clicked block is one of
  `rule.blocks`, else `None` (fall through). Resolve `rule.blocks` to block ids at rule-set time,
  with the same lookup `Block::set_dynamic_placement_rules` uses for `block-key`
  (`Block::from_registry_key`), and fail with the existing "unknown block" error.
* Reading a property uses the existing `DynamicBlockInfo::value(state_index, property)`
  (`block_registry.rs:1237`) on the clicked block's own `dynamic_info`, with the index from
  `info.state_index(state_id)`; a vanilla clicked block has no `dynamic_info` and gives `None`,
  so the rule falls through.

### Dart

`PlacementSourceKind.clickedBlockProperty` + a `ClickedBlock` record mirroring `ShaftNeighbour`,
and `PlacementRule.clickedBlockProperty(String property, List<String> blocks, {required String
readProperty})` (the rule's property and the clicked block's property are separate names).

### Unblocks

* linear/secondary chassis placed on a linear/secondary chassis (copy the clicked `axis`);
* harvester/plough/roller placed on another actor (copy the clicked `facing`).

Together with 6 (the horizontal-click condition) this makes both rules exact.

## 3. `clicked-horizontal-face`

### Java call sites

`content/logistics/funnel/BeltFunnelBlock.java:100-111`:

```java
Direction facing = ctx.getClickedFace().getAxis().isHorizontal()
    ? ctx.getClickedFace()
    : ctx.getHorizontalDirection();
```

`content/contraptions/actors/AttachedActorBlock.java:69-78` (the `else` branch):

```java
else
    facing = context.getClickedFace();
```

`content/logistics/itemHatch/ItemHatchBlock.java:70-81`:

```java
return withWater(state.setValue(FACING, pContext.getClickedFace().getOpposite()), pContext);
```

`clicked-face` cannot be used: the properties are four-value (`north/south/west/east`) and the
host rejects a rule whose source can give a value the property does not list.

### WIT

```wit
    variant placement-source {
        // ...
        /// The face of the clicked block when it is horizontal: `north`, `south`, `east`,
        /// `west`. Gives no value for a click on a top or bottom face, so the rule falls through
        /// to the next one.
        clicked-horizontal-face,
    }
```

### Host

* `PlacementSource::ClickedHorizontalFace`, `required_values` → `HORIZONTAL_NAMES`,
  `value` → `None` when `context.clicked_face` is `Up`/`Down`, else the name (or its opposite).
* `opposite` allowed.

### Dart

`PlacementSourceKind.clickedHorizontalFace` + `PlacementRule.clickedHorizontalFace(property,
{bool opposite, bool? whenSneaking})`.

### Unblocks

* belt funnels: `clicked-horizontal-face('facing')` then `horizontal-facing('facing')` as the
  fallback, which is exactly Java's ternary;
* attached actors: `clicked-horizontal-face('facing')` as the `else` branch (with 2 and 6 for the
  other two branches);
* item hatch: `clicked-horizontal-face('facing', opposite: true)`.

## 4. `refuse-when-clicked-face-axis`

### Java call site

`content/logistics/itemHatch/ItemHatchBlock.java:70-81`:

```java
public BlockState getStateForPlacement(BlockPlaceContext pContext) {
    BlockState state = super.getStateForPlacement(pContext);
    if (state == null)
        return state;
    if (pContext.getClickedFace().getAxis().isVertical())
        return null;
    // ...
}
```

`null` means the item is not placed at all; no state is written and no `onPlace` runs. A rule
list can only *set* properties, so today the hatch is placed on a top face and gets a facing.

### WIT

```wit
    enum block-axis {
        x,
        y,
        z,
    }

    record placement-rule {
        property: string,
        source: placement-source,
        opposite: bool,
        when-sneaking: option<bool>,
        /// Refuse the placement when the clicked face lies on this axis, like
        /// `getStateForPlacement` returning `null`. Checked before the state is built, so the
        /// block is not placed at all.
        refuse-when-clicked-face-axis: option<block-axis>,
    }
```

### Host

This must **not** be evaluated in `state_for_placement`: `BlockBehaviour::on_place` returns a
`BlockStateId` and cannot decline, and a plugin that writes the block away in `onPlaced` recurses
through the placed hook (commit `c5c4f7b`). The placement path already has the right place:

* `BlockRegistry::place_block` (`crates/pumpkin-core/src/block/registry.rs:706`, the check at
  `:777`) calls `self.can_place_at(...)` **before** `on_place`, and returns `Ok(None)` when it
  answers `false`.
* `DynamicBlock::can_place_at` (`crates/pumpkin-core/src/block/blocks/dynamic.rs:411`) is the
  plugin-visible half of that call. It currently returns `true` unless the block opted in to
  `BlockCallbacks::CAN_PLACE`; the veto must run for every block that has placement rules,
  independent of that callback:

  ```rust
  fn can_place_at(&self, args: CanPlaceAtArgs<'_>) -> bool {
      let Some(info) = args.block.dynamic_info() else { return true };
      if let Some(axis) = info.refused_placement_axis(args.direction) {
          return false;
      }
      // existing CAN_PLACE callback path
      ...
  }
  ```

* `args.direction` is the host's `final_face`, which points from the placed block toward the
  clicked one; `PlacementContext.clicked_face` is its opposite. The axis is the same either way,
  so the comparison is `args.direction.to_axis() == axis`.
* Validation: reject the field on a rule that would never be reached (a later rule for the same
  property) is unnecessary; keep it simple and only check the axis enum.

### Dart

`BlockAxis` enum, `PlacementRule.refuseWhenClickedFaceAxis` (or a
`PlacementRule.vetoOnClickedFaceAxis(axis)` convenience), and the wire mapping.

### Unblocks

The item hatch's vertical-click refusal. The rest of the hatch rule (3) then matches Java exactly.

**Fallback that works today:** `ItemHatchBlock` can opt in to `BlockCallbacks.CAN_PLACE` and return
`false` from `onCanPlace` for a vertical `e.face` — the hook is called on the player placement path
with the final face (`registry.rs:777`), so it cancels the placement correctly. It is a per-block
handler instead of a declarative rule, and it does not live with the other placement rules, which
is why the rule field is still the better shape.

## 5. `neighbour-shaft-axis` and `when-neighbour-shaft` (needed for exactness)

`RotatedPillarKineticBlock.getStateForPlacement` (`:68-80`) is the whole rule of the radial
chassis and the sneaking branch of the linear chassis:

```java
Axis preferredAxis = getPreferredAxis(context);
if (preferredAxis != null && (player == null || !player.isShiftKeyDown()))
    return defaultBlockState().setValue(AXIS, preferredAxis);
return defaultBlockState().setValue(AXIS,
    preferredAxis != null && player.isShiftKeyDown()
        ? context.getClickedFace().getAxis()
        : context.getNearestLookingDirection().getAxis());
```

`neighbour-shaft` yields a *direction*, which the `axis` property cannot hold, and no rule
condition can ask whether a shaft neighbour exists. Both are needed.

```wit
    variant placement-source {
        // ...
        /// The axis of the neighbour that has a shaft pointing into the placed block: `x`, `y` or
        /// `z`. Gives no value when no neighbour has one, or when two lie on different axes (the
        /// give-up of `getPreferredAxis`). `opposite` is not allowed.
        neighbour-shaft-axis(list<shaft-neighbour>),
    }

    record placement-rule {
        // ...
        /// Only apply the rule when such a shaft neighbour exists (`present: true`) or when none
        /// does (`present: false`). None always applies.
        when-neighbour-shaft: option<neighbour-shaft-condition>,
    }

    record neighbour-shaft-condition {
        /// The neighbours that count, with the same meaning as for `neighbour-shaft`.
        shafts: list<shaft-neighbour>,
        /// `true`: apply only when at least one counts; `false`: only when none does.
        present: bool,
    }
```

Exact linear chassis, in Java order (item 2 first, then these four):

```dart
// isChassis(clicked) && !sneaking -> clicked AXIS
PlacementRule.clickedBlockProperty('axis', chassisKeys, whenSneaking: false),
// preferredAxis != null && !sneaking -> shaft axis
PlacementRule.neighbourShaftAxis('axis', chassisShaftNeighbours, whenSneaking: false),
// preferredAxis != null && sneaking -> clicked face axis
PlacementRule.clickedAxis('axis',
    whenSneaking: true,
    whenNeighbourShaft: ShaftPresence(chassisShaftNeighbours, present: true)),
// no preferredAxis (sneaking or not) -> look axis
PlacementRule.lookingAxis('axis'),
```

Radial chassis is the last three rules without the clicked-block rule. The first two rules need no
condition (their sources give no value without a shaft); the third needs the explicit `present:
true`, because `clicked-axis` always gives a value. The condition carries its own shaft list so a
chassis next to a bearing is counted like Java's `instanceof IRotate` does; a default of
`create:shafts` would miss that.

## 6. `when-clicked-face-axis` (needed for the attached actors)

`AttachedActorBlock.getStateForPlacement` reads the clicked block only in the `else if`, i.e. only
for a horizontal click:

```java
if (context.getClickedFace().getAxis().isVertical())
    facing = context.getHorizontalDirection().getOpposite();
else if (blockState.getBlock() instanceof AttachedActorBlock)
    facing = blockState.getValue(FACING);
else
    facing = context.getClickedFace();
```

Without a condition, `clicked-block-property` would copy a neighbour actor's facing for a click on
a top face too, which Java does not do.

```wit
    enum axis-filter {
        x,
        y,
        z,
        /// `x` or `z`.
        horizontal,
        /// `y`.
        vertical,
    }

    record placement-rule {
        // ...
        /// Only apply the rule when the clicked face lies on a matching axis. A rule that does not
        /// apply leaves the property to the next rule. None always applies.
        when-clicked-face-axis: option<axis-filter>,
    }
```

Exact attached actors:

```dart
// clicked face vertical -> horizontal look, opposite
PlacementRule.horizontalFacing('facing', opposite: true, whenClickedFaceAxis: AxisFilter.vertical),
// clicked face horizontal, clicked block is an actor -> its FACING
PlacementRule.clickedBlockProperty('facing', actorKeys,
    whenClickedFaceAxis: AxisFilter.horizontal),
// clicked face horizontal, otherwise -> the clicked face
PlacementRule.clickedHorizontalFace('facing'),
PlacementRule.inWater('waterlogged'),
```

This field also lets the belt funnel and the item hatch drop the `whenSneaking`-style workarounds
they do not need, and it is the same mechanism the veto would use if the veto were expressed as a
skip rather than a refusal.

The `placement rules the host cannot express` group asserts the current fallback; each test there
is deleted when its addition lands, and the `_describe` pins in `the rules are the ones the Java
placement needs` change with the rule lists.
